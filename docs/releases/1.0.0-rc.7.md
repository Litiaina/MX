# MX 1.0.0-rc.7 — 2026-10-21

[Documentation](../README.md) · [Validation](../../TESTING.md) · [Changelog](../../CHANGELOG.md)

**Release candidate, not stable 1.0.0.** Fixes module attachments being blocked
above 50 MiB even after increasing the server configuration. Published RC.6
and all earlier assets remain unchanged.

## After installing

1. Save active work and install through **Administration → Updates** using the
   normal signed-update procedure, or your saved maintenance policy.
2. Refresh the main MX tab. Open **Administration → Deployment → Upload limits**.
3. Under **Module record attachments**, select **No file-size limit**, or
   **Custom limit** and **100** MiB (sufficient for a 66 MB file), then choose
   **Save upload limits**.
4. Retry the attachment. The form displays the actual current limit; new
   uploads use saved settings immediately, with no additional restart.

Collaboration file limits are configured separately. **Server default** removes
an override and uses `mx.config [n1] attachment_max_size_mb` or
`collaboration_file_max_size_mb`. Editing `mx.config` itself still requires
restarting MX. Saved administrator overrides take precedence and survive
restarts/updates. Review a reverse proxy's request-body allowance if it returns
HTTP 413; MX settings cannot override the proxy.

## Fixes and safety

- Remove the record form's hard-coded 50 MiB limit, including copies from Drive.
  Refresh the server policy when choosing files and show rejection details next
  to the attachment controls rather than requiring users to find a distant error.
- Add explicit administrator controls, current enforced sizes and Server
  default/custom/No file-size limit choices. Reject invalid/stale saves; an old identity form
  cannot erase a newer upload policy. Preserve unsaved policy controls through
  live reconnect/global refresh.
- Apply one effective policy to browser metadata, HTTP-body guards and file
  reads. Stop oversized/chunked uploads before N1, with actionable JSON errors.
- Retain existing permissions, file/history metadata, multipart N1 behavior and
  original downloads. No Drive per-file cap is added. Drive quotas, import
  budgets and Office memory budgets remain separate.

Record/chat files stage on private temporary disk and transfer to N1 in bounded
parts. Ensure MX's temporary disk has capacity for concurrent uploads. Both
startup limit settings also accept `0` for no per-file cap. Prefer Drive's
resumable path for very large files. The real 66/101 MiB acceptance tests are
not an unlimited-storage or throughput guarantee. Existing RC.6 Office/browser and notification limits
still apply; see [validation](../../TESTING.md).

## Package and upgrade boundaries

New installation: `mx-1.0.0-rc.7-x86_64-unknown-linux-gnu.tar.gz`.
Managed/offline update: `mx-x86_64-unknown-linux-gnu.mxupdate` plus signed
`mx-x86_64-unknown-linux-gnu.json`. Publisher key remains `fdf69f67562fb715`.
The independent worker, final SQLite backup and failed-activation rollback
protocol are unchanged. Rollback restores the paired previous application and
its verified pre-update SQLite snapshot, not an older binary alone.

No new database schema or N1 format migration is introduced. Override values
live in existing deployment configuration JSON. N1 stays independently versioned
at `1.0.0-RC.1`, NOA v1, storage encoding 4. Publication does not deploy to or
restart any production server.
