# MX 1.0.0-rc.5 — 2026-10-20

[Documentation](../README.md) · [Validation](../../TESTING.md) · [Changelog](../../CHANGELOG.md)

**Release candidate, not stable 1.0.0.** Published with maintainer authorization
as `v1.0.0-rc.5`, using the existing Ed25519 publisher key and signed-update
protocol. Existing deployments can stage it through Administration → Updates
or upload the signed offline package. Installation follows their saved policy;
publication itself does not restart a deployment.

From RC.4, use **Check for updates → Download and verify → Install now…**, or
your saved automatic maintenance policy. The publisher key remains
`fdf69f67562fb715`. New installations use
`mx-1.0.0-rc.5-x86_64-unknown-linux-gnu.tar.gz`; managed/offline updates use
`mx-x86_64-unknown-linux-gnu.mxupdate` with its signed `.json` metadata.

## Scope

- Full-record editing and direct contextual record sends to a person.
- Account-specific bold fields and effective enlarged text, including 200%.
- Explicit module library, separate create/configure workflows and dirty guards.
- Combined-text calculations usable in searchable relationship labels/auto-fill.
- Independent select codes, labels and numeric values for arithmetic.
- Filtered incoming totals and live balance formulas without repeated deductions.
- Opt-in creator-only records and creator/admin-only field access.
- Focus-aware desktop notifications, missed-message recovery, deduplication and
  honest permission/browser/OS diagnostics.
- Correct Collaboration People highlighting on new deployments: no selected
  conversation means no highlighted people, not every person selected.

Use the worked [calculations/privacy guide](../calculations-and-privacy.md) and
[desktop notification guide](../desktop-notifications.md). These features add no
organization-specific modules or starter data.

## Upgrade and rollback boundaries

Back up before deployment. Ownership metadata is additive and reconstructed from
genuine creation/import evidence, never from the last editor. Existing records,
fields, files, credentials and module-wide visibility are preserved by default.
Historical rows without creator evidence remain administrator-only if you later
enable creator-only access; review them before changing that policy.

After using new privacy/calculation settings, **do not run an older binary against
the modified database**: it does not implement these controls or calculation
formats. Roll back the paired binary/frontend and its verified pre-update database
snapshot together, through the established updater/operator procedure.

N1 remains an independent service. This candidate changes neither N1's source nor
storage format, fragment keys, object ownership or object-version strategy.

## Acceptance boundaries

Passing automated checks is not a promise of zero defects. In particular, real
Windows desktop banners need validation with the deployment's trusted HTTPS
certificate, browser permission and OS policy. Headless browser instrumentation
can verify routing but cannot prove visible OS delivery. MX must remain open;
there is no internet-dependent push service for closed/discarded clients.

Live totals reflect accessible current records, not a permanent financial ledger
or transactional approval/overdraft-prevention workflow. Cross-record recursive
aggregates are intentionally rejected. Live linked calculations are not stored
search/sort columns or authoritative CSV balance snapshots.

The release-readiness verdict and remaining manual checks are maintained in
[TESTING.md](../../TESTING.md). Target-client acceptance is still required before
claiming stable-release qualification; publication does not waive those limits.
