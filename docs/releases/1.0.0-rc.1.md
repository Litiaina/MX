# MX 1.0.0-rc.1

[Documentation index](../README.md) · [Migration policy](../migration-and-releases.md) · [Changelog](../../CHANGELOG.md)

**Release date:** 2026-10-16 (Asia/Manila); candidate preparation began 2026-10-15.

**Status:** release candidate for evaluation; not the final stable 1.0.0.

**Rust/frontend version:** `1.0.0-rc.1`

**Release tag:** `v1.0.0-rc.1`

**N1 compatibility:** v4.0.0 / storage format 4, independently versioned.

Preparing this candidate in the repository does not itself publish a GitHub
release, create a tag, sign a package or update a running installation.

## What the version reset means

The maintainer is starting the official release line at 1.0. Earlier MX labels,
including the 4.x development line, remain part of the project's history. This
candidate includes that existing functionality; it is not a return to an older
codebase. Preserve all old tags and release artifacts rather than relabeling them.

The reset changes application/package identification only. It does not change
SQLite migration state, database paths, record revisions/history, schema IDs,
N1 fragments/object keys, deployment branding, credentials or `/mx/v1` routes.
Do not reset data to make its version resemble 1.0.

Subsequent fixes should be released as `1.0.0-rc.2`, `1.0.0-rc.3`, etc. Publish
`1.0.0` only after the stable-release acceptance gates are satisfied. Never
replace the contents of an already published tag/package under the same version.

## Candidate scope

- Configurable modules, fields, relationships, lookups, rollups, relationship
  auto-fill, conditional forms and numeric column summaries.
- Stateless optimistic record concurrency, normal record history, access
  controls, bounded cursor browsing with stable scroll positions and a paged
  fallback. Full long-text wrapping and compact navigation controls.
- Spreadsheet import with per-sheet mapping, row validation, inspectable skips,
  correction/retry and durable import history.
- Drive ownership/quotas, resumable transfers, versions, authenticated user/group
  sharing, public guest links and collaboration sharing notifications.
- Collaboration messaging, calls, camera/screen sharing and media recovery,
  subject to the qualification limits below.
- Locally bundled browser Office editing, honest load/save feedback, idle saves
  and recovery checkpoints. MX owns file versions; N1 stores each as a new object.
- SQLite backups in N1, integrity checks and visible backup/verification activity,
  including status reconciliation after lost acknowledgements.
- Opt-in signed update discovery/download, signed offline packages and matching
  application slots. An independent Linux/systemd worker supports manual or
  configurable maintenance-window installation, final local backup, activation
  checks and paired application/database rollback. See [setup and trust policy](../updates.md).

Read [CHANGELOG.md](../../CHANGELOG.md#100-rc1---2026-10-16) for the detailed changes.
MX remains a standalone server with SQLite and N1. Packaged deployment needs no
Cargo/Node installation or separately installed Office server, and normal LAN
operation does not require public internet access.

## Release assets and initial installation

The published `x86_64-unknown-linux-gnu` build is for Linux x86-64 with
**glibc 2.39 or newer**, OpenSSL 3 (`libssl.so.3`, `libcrypto.so.3`), zlib
(`libz.so.1`), Zstandard (`libzstd.so.1`) and the standard GCC runtime
(`libgcc_s.so.1`). It is not a static or universal Linux executable. Older
distributions need a qualified source build; no ARM, macOS, Windows or musl
binary is published in this candidate.

- `mx-1.0.0-rc.1-x86_64-unknown-linux-gnu.tar.gz`: initial-install archive with
  the optimized executable, matching frontend/Office resources, documentation,
  branding and deployment templates. No live database, credentials, TLS private
  keys or N1 data are included. Follow the [deployment guide](../deployment.md);
  this archive does not silently install services or overwrite an existing site.
- `mx-x86_64-unknown-linux-gnu.mxupdate` and `mx-x86_64-unknown-linux-gnu.json`:
  signed package and metadata for the [provisioned updater](../updates.md).
- `mx-release-signing-public-key.json`: publisher public key only. Compare its
  fingerprint with an independently trusted channel before adding it to
  `trusted_keys`; never install or share the publisher's private signing key.
- `SHA256SUMS`: checksums for the downloadable release assets.

No `.deb` installer is included. Initial installation and the 4.x release-line
transition remain operator-driven. A newer signed candidate can subsequently
use the configured manual or maintenance-window update policy.

## Not included or not guaranteed

- **Unprovisioned installations cannot self-update.** The deployment operator
  must install managed slots/independent worker units and a trusted public key
  before choosing automatic mode. No private release key or vendor trust decision
  is silently installed. Existing 4.x crossgrades remain manual.
- General database restoration remains an offline administrative procedure.
  The updater's automatic restore is restricted to failed activation behind a
  write barrier; the Backups page is not an unattended recovery system.
- Office is an additional client-side feature, not a guarantee of a complete
  Office suite or real-time document co-editing. Presentation editing is not
  qualified. The tested Linux WebKit offers a download fallback rather than
  Office editing; this is not a Safari/macOS/iOS qualification.
- Recovery checkpoints are not a zero-loss power-cut guarantee. Edits after the
  last completed checkpoint may be lost, and complex document parsing/export can
  remain slow on client devices.
- Focused automated passes do not establish a complete live-N1 durability,
  real-device media, accessibility or security qualification.

## Upgrading a 4.x development installation

This is an **explicit one-time release-line transition**, not an ordinary
numerically increasing upgrade: semantic version comparison places 1.0.0-rc.1
below 4.x. Do not disable downgrade checks globally or reset migration markers.

1. Read the [deployment guide](../deployment.md), current limitations and test
   evidence. Plan a maintenance window; save/download any open Office edits.
2. Drain active writes and background jobs, then stop MX. Keep normal writes
   blocked until candidate validation is finished.
3. Create and verify the [final rollback snapshot](../deployment.md#taking-the-final-rollback-snapshot), then retain it with the previous binary/frontend,
   `mx.config`, `mx.env` and TLS files. Keep the rollback database locally as well
   as any N1 copy. Preserve N1 storage separately: a SQLite backup contains file
   metadata/references, not all attachment/Drive object bytes.
4. Install the matching candidate executable and `frontend/dist` together. Keep
   the existing database and configuration paths. Do not replace them with
   empty templates, regenerate credentials or reset N1. N1 needs no version
   reset to match MX.
5. Start the candidate under restricted maintenance access. Inspect migrations
   and startup errors; verify authentication, permissions, records/history,
   relationships, a file download and backup visibility before reopening users.
6. If activation fails before reopening writes, stop the candidate and restore
   **both** the previous release and the verified pre-update database. Never
   replace a database while a server still has it open; preserve the failed
   state for diagnosis and follow the [offline rollback procedure](../deployment.md#manual-rollback-during-failed-activation)
   for SQLite WAL/SHM files. This rollback is manual in this candidate.
7. After successful validation, reopen normal access. Do not silently restore
   the pre-update database after new user writes have resumed: that would erase
   acknowledged work saved since the backup.

For this initial manual crossgrade, the deployment administrator must enforce
restricted access and writer quiescence using service/network controls. Subsequent
updates can use the [provisioned signed updater](../updates.md); installing this
candidate does not silently adopt an existing unmanaged deployment.

## Building and checking the candidate

The frontend build verifies that Cargo/frontend manifests, lockfiles and the
README agree on version/channel. Dependency versions are not changed by this
reset. For normal builds, follow [build instructions](../../README.md#build-from-source).

```bash
npm --prefix frontend run check:release
npm --prefix frontend test
cargo test --locked
npm --prefix frontend run build
cargo build --release --locked
./target/release/litiaina-mx --version
```

The final command must print `litiaina-mx 1.0.0-rc.1` without opening a database,
creating configuration or contacting N1. Tests may need the external build and
artifact locations documented in [TESTING.md](../../TESTING.md); do not run
live-storage or physical-audio tests against real deployments without an
explicitly isolated test environment.

## Gates before stable 1.0.0

1. Freeze a candidate and qualify the same binary/frontend artifact together,
   including real-N1 uploads/downloads, resume, concurrency, ACLs and guest links.
2. Demonstrate an actual restore of a representative deployment, validating
   SQLite **and** referenced N1 files, and exercise failed-upgrade recovery.
3. Close or explicitly scope browser/Office/media limitations against the
   supported devices; reconcile historical failures with newer passes rather
   than silently treating them all as fixed.
4. Run sustained network/storage interruption and capacity checks. Current
   injected-fault tests are not physical power-loss or disk-failure certification.
5. Review security, the pinned Office engine's support status, corresponding
   source/distribution obligations and complete third-party/font notices before
   public binary distribution. Bundled license texts alone are not that audit.
6. Review installation, migration, recovery and operator instructions, then
   decide stable scope, including signing-key operations and update/rollback on
   each supported deployment/service mode. A manual-upgrade-only deployment need
   not enable the optional updater.

[TESTING.md](../../TESTING.md) is the evidence ledger. Its dated older sections
retain failures and limits for their original artifacts; newer focused passes
supersede only the scenarios they actually repeat. No version rename closes a
release gate or constitutes production certification.
