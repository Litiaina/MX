# MX 1.0.0-rc.10 — 2026-10-27

[Documentation](../README.md) · [Validation](../../TESTING.md) · [Changelog](../../CHANGELOG.md)

**Release candidate, not stable 1.0.0.** This is a concurrent-save and reliability
hotfix. Published RC.9 and earlier assets remain unchanged. Publication does not
deploy or restart an existing server.

## What changes

- **Record saves:** fair writer admission, independent readers and permission
  rechecks reduce contention during concurrent record, workflow and book work.
  Notification fan-out moves to a durable batched outbox, with current privacy
  and notification preferences checked before delivery and restart recovery.
- **False uniqueness conflicts:** a hidden legacy control-number constraint no
  longer makes a module's ordinary `control_no` field implicitly unique.
  Repeated non-unique values work within and across modules; stale/missing
  internal sequence state reconciles during the transaction. Existing records,
  visible numbers, relationships and histories are not changed. Explicit unique
  fields remain unique and a rejected create/edit identifies the field.
- **Files:** independent immutable object keys protect a successful same-name
  attachment from a competing upload's cleanup. A shared eight-transfer default
  bounds active N1 work; `[n1] max_concurrent_uploads` accepts 1–64. Waiting
  uploads stay disk-spooled. Supported paths preserve upstream busy/timeout
  status and retry guidance instead of a misleading generic 502.
- **Live/admin:** account-routed private events preserve ordering; bounded
  credential workers handle login bursts. Background refresh/reconnect no
  longer destroys the selected administration module or its unsaved draft.
- **Imports:** bounded process batches report committed progress during active
  editing. Invalid rows remain inspectable; infrastructure failures pause work.

## Upgrade an existing deployment

1. Save active forms/documents and pause new imports/transfers. Retain a verified
   SQLite backup, deployment configuration and an independent N1 recovery copy.
   SQLite references files; it does not contain their original N1 bytes.
2. In **Administration → Updates**, check for updates, download/verify
   **1.0.0-rc.10**, then use **Install now…**, or the configured maintenance policy.
   Use the matching signed executable/frontend pair. Do not reset, recreate or
   re-import the database and do not delete records to work around a conflict.
3. Startup creates the additive notification-outbox table before opening business
   routes. Keep the updater's verified final pre-update snapshot and previous
   application slot. Existing modules, grants, schemas, values and files remain.
4. Refresh older MX tabs. Confirm the installed version is `1.0.0-rc.10`; open an
   existing module, save one legitimate new record, edit it, inspect history and
   download an existing attachment. Check a second account's notification inbox.
5. If a save still fails, keep the draft and capture the exact message and action
   for the operator. An explicitly unique field now names itself. An unexpected
   stored-data constraint is logged privately; it must not be guessed away by
   deleting data. After a timeout, reconcile the original operation rather than
   blindly submitting a second business record.

New installation: `mx-1.0.0-rc.10-x86_64-unknown-linux-gnu.tar.gz`.
Managed/offline update: `mx-x86_64-unknown-linux-gnu.mxupdate` and signed
`mx-x86_64-unknown-linux-gnu.json`. Assets also include checksums, publisher public
key and build provenance. No new runtime service or Internet dependency is added.

## Compatibility and rollback

Publisher key **fdf69f67562fb715**, package format 1, the independent worker and
the paired final-backup/rollback protocol are unchanged. N1 is independently
versioned **1.0.0-RC.1**, NOA v1, storage encoding 4. This package does not upgrade
N1, modify its configured limiter or rewrite existing object keys.

Failed activation restores the previous executable/frontend and verified SQLite
snapshot together. Do not downgrade only the executable against an upgraded
database. Restoring a pre-update snapshot after accepting new work would discard
that work and requires an explicit recovery decision.

## Validation boundaries

The final versioned executable passed **237 native tests** (two opt-in tests
ignored), **385 frontend tests**, targeted save-conflict/upgrade/CLI regressions
and four-browser update/admin-draft checks. Its real 100-account API/WebSocket
run completed **33,123 requests with zero unexpected failures**, including a
1,000-row import with active users, exact file bytes and process-crash recovery.

The [qualification report](../concurrency-qualification.md) identifies real
100-account API/WebSocket workloads, exact executable hashes, deadlines,
file-byte checks, concurrent imports, privacy, journals/stock, process crashes
and repeat results. It also records failed attempts rather than hiding them.
The latest selected N1 source is `90f436ff54a6b67fe892235cdbd6424503eca353`.

The 1,000-user overload attempt failed response deadlines; do not advertise
1,000-user capacity. The shared-HDD runs are not a low-latency SLA, qualification
of every production machine or 100 full browser/Office renderers. Process-kill
recovery is not physical power-loss qualification. Desktop-notification tests
instrument delivery APIs, not physical Windows banners. Linux WebKit without
worker WebGL uses an explicit original-download fallback. This release does not
certify every custom business policy, document or hardware environment.
